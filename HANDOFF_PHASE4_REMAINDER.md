4. **Phase 5**: the fidelity pass, `PORT_METHOD.md` updates, and the repeatable-pipeline check.

## `Synth::render`: the port plan the decompilation supports

The Ghidra C (`analyzeHeadless /tmp/ghidra-p4 p4 -process libSnakePlugin.so -noanalysis`, filter
`Synth::render`) is 2 350 lines and usable once the register noise is skipped. Its shape:

1. **Setup** (C lines 1260-1700): `memset` a 0x400-byte scratch at `this + 0x288`, zero a 0x200-byte
   scratch at `this + 0x688`, then read the plug flags (`PlugManager::getPlugFlags` twice), the module
   sends, the active track, the input selector, the BPM four times, and `get_time_monotonic` twice.
2. **The track loop** (`do { } while (track != 8)`, C lines 1700-2070): for every track 0..7
   * track 6 is the FX/master slot: the parameter blocks at `+0x5c78`..`+0x5c90`, `+0x60f8`.. and
     `+0x5c98`.. are copied into the scratch and two scratch words are set to `0x3fffffff`;
   * otherwise two `Lfo::render` calls: layer 1 at `this + track*0x2c + 0x4ee4` with the block at
     `+0x5f48` and out `this + 0x15a0`, then layer 0 at `+0x4d00` with the block at `+0x5ac8` and out
     `this + 0x1554` (both LFOs take `this + track*4 + 0x6ca4` as an input);
   * two `InstrumentManager::vibrato` calls, on `clamp(this+0x15a0's first word + 0xc0000001) << 1`
     and on `clamp(this+0x1554's first word * 2 - 0x7ffffffe)`;
   * zero the 0x200-byte mix buffer at `this + 0xf08`, then `InstrumentManager::render(track, 0, mix,
     this + 0x1554, &counter)` and the same for layer 1 with `this + 0x15a0`;
   * a per-track halfword counter at `this + track*2 + 0x6aac` and a per-track value at
     `this + track*4 + 0x5108`, and the mix-down into the accumulation buffers at 0x1227a20/0x1227e20
     (four track groups of 0x200 bytes) plus the scratch at 0x1228020/0x12284a0, with the layer-0/1
     modulation blocks at 0x1228cec and 0x1228d38 handed to the voices as their parameter block;
   * the four `FxManager::render` calls, five `trackFilterProcess` and six `trackFilterDcBlock`.
3. **The master tail** (C lines 2070-3610): `bounceAudio`, the four `Sequencer::getBPM` reads, the two
   `masterCompressor`-style blends over the mix buffers at `this + 0xee8`/`0xf08`/`0x1108`, the VU
   words, and the writes into the four output buffers the caller passed.

The scratch the function touches is **not** inside the object: the mix buffers and the modulation
blocks are separate `.bss` objects addressed absolutely - 0x1227a20 (0x400, `memset`), 0x1227e20,
0x1228020, 0x12284a0, 0x12286a0, 0x12288a0, 0x1228aa0 (`inputBuffer`), 0x1228cec and 0x1228d38 - so
the port owns one buffer spanning 0x1227a00..0x1228e00 (0x1400 bytes, 1 280 words) and indexes it by
device offset, while the `Synth` object itself stays wherever its owner puts it. (An earlier reading
of these as `this + 0x288` and friends was wrong: `memset(&DAT_01327a20, 0, 0x400)` would have wiped
the voice array at `this + 0x480`, which the device plainly does not do.)

The fixture is already in place: `synth_render_fixtures` in `make_host_fixtures.py` keeps the object
in an allocation and the scratch in the library's `.bss`, stubs one engine render for all 132 voice
slots - the stub *fills* the engine's block from the increment, so the mixer has signal to scale -
and records 8 cases. `synth_render_fixture_is_alive` in `host.rs` checks it drives the real thing
until the port can replay it.

`Synth::render`'s signature is `(fract32_t *a, *b, *c, *d)`; the four blocks are the main output
plus the two FX returns and the sidechain the master compressor reads.

### What `Synth::render` does, in the order the C shows it

Measured from the decompilation (line numbers are the C's), with the **v1-reachable** path marked; the
input-signal, sampling, tone-mode and song-mode branches are gated on host flags the clone fixes at
zero, so they are documented rather than ported (the plan's `PORT_METHOD.md` rule).

1. **Setup** (1 500-1 700): `mutex_lock(this + 0x6864)`, `interpolateParameters`, then four master
   words at `+0x684c`/`+0x6850`/`+0x6854`/`+0x6858`, each folded one step toward a byte the song
   fixture carries (`master_params[0..4]`, the same 64th-order IIR `interpolateParameters` uses);
   `get_time_monotonic`; the module's two plug ids (`+0x60`, `+0x6c`) through
   `PlugManager::getPlugFlags`; `*(u64 *)(this + 0x6c40) = [0x7fffffff - *(u32*)(this+0x5d38),
   0x7fffffff - *(u32*)(this+0x5d80)]`.
2. **The track loop** (1 700-2 070), eight iterations, all reachable:
   * track 6 skips the LFOs and copies the FX/master parameter blocks (`+0x5c78`, `+0x5c80`, `+0x5c88`,
     `+0x5c90`, `+0x5c98`.., `+0x60f8`..) into the two modulation blocks and sets two words to
     `0x3fffffff`;
   * otherwise two `Lfo::render` calls - layer 1 at `+0x4ee4` with the block at `+0x5f48`, layer 0 at
     `+0x4d00` with `+0x5ac8` - with the modulation blocks as their `out` and `this + track*4 + 0x6ca4`
     (+`0x6c78`/`+0x6c4c` as the accelerometer inputs);
   * two `InstrumentManager::vibrato` calls (layer 0 from `+0x6c78`'s word, layer 1 from `+0x6c4c`'s);
   * `InstrumentManager::render(track, 0, mix, mod0, &counter)` and the same for layer 1 with `mod1`;
   * `trackFilterProcess` on `this + track*0x2c + 0x688c` and `trackFilterDcBlock` on
     `this + track*0x18 + 0x69ec`, both over the mix buffer and into the group sums;
   * the mix-down: each sample of the track mix is scaled by the track's gain (from `+0x50c8`,
     `+0x5148`, `+0x5108`, `+0x5188` and the two group gains `local_88`) with the `mul31` chains and
     saturating adds, accumulated into the group sums at `0x1227a20` (tracks 0-3) and `0x1227c20`
     (tracks 4-7), with per-track peaks at `this + track*2 + 0x6c10` and per-group peaks in the
     `local_a8` block (decayed by `* 0x7ed9 >> 15`).
3. **The master mix** (2 090-2 140): `param_1[i] = softclip(sat_add(group0[i], group1[i]))` where
   `softclip(x) = sat_add(x, sat_sub(x, mul31(mul31(x*x) * x)) >> 1)`. The C has a second, vectorised
   copy of the same arithmetic for the case where the output does not alias the sums.
4. **The FX sends/returns** (2 140-2 870): four `FxManager::render` calls with the plugs the manager
   has loaded. **v1 has none**, so each is a no-op, but the buffers around them (`0x12284a0`,
   `0x12288a0`, `this + 0xee8`..) and the `trackFilterProcess`/`trackFilterDcBlock` pairs after them
   still run.
5. **The master tail** (2 870-3 610): `param_1 += 0x12288a0`; `FxManager::render(0xb, this+0x5de0,
   param_1, ...)`; two more `trackFilterProcess`/`trackFilterDcBlock`; `bounceAudio`; the four
   `getBPM` reads and the `UNK_0017d064` table lookups that become `masterCompressor`'s four
   reference arguments; `masterCompressor(0x12288a0, ...)`; the master gain from
   `g_compressorLevel` and `this + 0x6854`/`0x6858`/`0x6264`/`0x6298`/`0x629c`; a soft limiter over
   the master buffer; the VU words; and the writes into the four caller buffers.

The two `(this + 0x6c10)`/`local_a8` peak paths and the four master words are pure bookkeeping: they
change no audio, but the fixture records them, so they must match too.

### The mixer's scratch, resolved

| object | address | offset in the port's span | role |
|---|---|---|---|
| group sums | 0x1227a20 (+0x200 per four-track group) | 0x20 | the master accumulation, summed into the output |
| send A | 0x1227e20 | 0x420 | an FX send per group |
| send B | 0x1228020 | 0x620 | the input-signal scratch (`g_renderInputSignal` only) |
| send C | 0x12284a0 | 0xAA0 | the third send |
| track mix | 0x12286a0 | 0xCA0 | what the voices render into |
| track filtered | 0x12288a0 | 0xEA0 | the DC blocker's output and the mix-down's input, later the master buffer |
| input buffer | 0x1228aa0 | 0x10A0 | the mic path, never filled in v1 |
| modulation 0/1 | 0x1228cec / 0x1228d38 | 0x12EC / 0x1338 | the two LFO blocks the voices read |

The tail, exactly: `param_1 += 0x12288a0` for the three FX-track mixes (8/9/10, each DC-blocked into
it first) and the master FX return; `trackFilterDcBlock(this + 0x6bb4, param_1, 0x12288a0)` moves the
sum into the master buffer; `bounceAudio` taps it; `masterCompressor(0x12288a0, ...)` compresses it in
place; then per sample

```text
g   = clamp(mul31_arith(this[0x6858]^2) * 0x5fffffff >>u 31) + 0x20000000     // the master gain
x   = clamp(master[i] * g * 2 >>a 0x1e & ~3)                                  // gain applied
y   = sat_add(x, sat_sub(x, mul31(mul31_arith(x^2) * x)) >> 1)                // soft clip
out = sat_add(mul31(x * (0x7fffffff - this[0x6264])), mul31(y * wet))         // dry/wet blend
peak = max(peak, out)                                                         // the VU word
out = min(0x7fffffff, mul31(this[0x6860] * out))                              // the master volume
```

`wet` is the BPM-table interpolation (`UNK_0017d064`/`+0x68`, two eight-entry `i32` tables at
0x7d064) and the compressor's third and fourth reference arguments come from `this + 0x629c` and that
table. The table is `.rodata` and belongs in a generator.

### The track loop's mix-down, decoded from the disassembly

The C for this loop reuses registers past the point of readability, so this comes from the asm at
`Synth::render+0x91c` (0xf830c..0xf84ec):

```text
per track t (the group is t >> 2, the group gain `local_88[group]`):
  ramp  = [this[t*4 + 0x50c8], this[t*4 + 0x5148]]      // lane 0: level, lane 1: pan
  target = [this[t*4 + 0x5108],
            mul31_logical(mul31_logical(mul31_logical(g1 * g2) * g3) * g4) * this[t*4 + 0x5188] >>u 31]
  step  = sqsub(target, ramp) >>a 7 per lane            // 64 frames to converge
  mix   = 0x12288a0                                     // the DC blocker's output, in place
  for i in 0..128:
      product = mix[i] * group_gain
      gain = product == 2^62 ? 0x3fffffff8 : (product >>a 28) & ~7
      gain = clamp(gain, -0x80000000, 0x7fffffff)
      a = mul31_arith(gain * ramp[0])                   // `sbfx #31` + sentinel, no clamp
      b = mul31_logical(gain * module_gain)
      sum0[i] = sat_add(sum0[i], mul31_logical(a * ramp[1]))          // 0x1227a20 + group*0x80
      sendA[i] = sat_add(sendA[i], mul31_logical(a * gain_a))         // 0x1227e20
      sendB[i] = sat_add(sendB[i], mul31_logical(a * gain_b))         // 0x1228020
      sendC[i] = sat_add(sendC[i], mul31_logical(a * gain_c))         // 0x12284a0
      out2[i]  = sat_add(out2[i], mul31_logical(b * gain_d))          // the caller's second buffer
      ramp += step                                      // after the samples are read, not before
  this[t*4 + 0x50c8] = ramp[0]; this[t*4 + 0x5148] = ramp[1]          // the ramp carries across blocks
  peaks at this[t*2 + 0x6c10] and `local_88`                          // decayed by * 0x7ed9 >> 15
```

The gain words come from the module-sends structure the sequencer holds (`getModuleSends` returns a
pointer; the mixer reads a halfword at `+0x1760` and words at `+0x1b58`/`+0x1b5c`/`+0x1b60`), from
`this + 0x6c48`, from the mute bit in `this + 0x6848` and from the two LFO blocks at `this + 0x1554`/
`+0x15a0`. The four accumulator gains (`gain_a`..`gain_d`) are four `mul31` chains over those, which
is the one part still worth reading line by line from the asm when the port lands.

`param_2` (the caller's second buffer) is written by this loop, so v1 - which has no FX tracks -
still has to produce it byte for byte for the fixture to pass.

### The mixer's state, measured while the loop was driven

* The `FxManager` has **four** slots (`FX tracks 8..11`): `0x4940 + 4 * 0xf0 = 0x4d00`, exactly the
  LFO array. Writing a fifth slot wipes the LFOs (a fixture bug that produced a very confusing diff).
* The LFO array is at `+0x4d00` with a `0x2c` stride and a **layer stride of eleven slots**, so slot 8
  is track 8 of layer 0 - the master LFO the tail renders at `+0x4e60`, `+0x4e8c` and `+0x4eb8` with
  the blocks at `+0x5d08`, `+0x5d50` and `+0x5e70`. The loop itself renders only tracks 0..7.
* The layer-1 modulation block's `out` buffer reaches `0x1228e88` (its 84th word), past the block, so
  the mixer's scratch span has to be `0x1500` bytes from `0x1227a00`.
* `Synth::resetLfo` takes the track, the layer and the caller's `params`, and uses the *Synth's*
  smoothed block for the LFO's parameters while writing the LFO's output into the caller's buffer -
  which the voices are also reading as their parameter block. A re-trigger therefore changes what the
  voices after it read. The port keeps its own copy of the modulation block per track and writes it
  back when the track's voices are done, which the mix-down sees; a voice rendering after a
  re-trigger inside the same block reads the pre-reset block. That is the one deviation, and
  `PORT_METHOD.md` records it.
* The port's `Voice` models the record from `+0x20` on; `+0x00`..`+0x1f` (the engine's area and the
  three entry points) is replaced by the trait dispatch, so a whole-mixer comparison has to zero those
  eight words on both sides.

### Where the mixer's loop stands

`render_tracks` is written and driven by `synth_render_tracks_match_the_original`, which is
`#[ignore]`d while it converges. It currently reports, per case, in this order:

| region | first diff | what it means |
|---|---|---|
| ~~a voice's `+0x174`~~ | fixed | the `centsDetune` aliasing, above |
| the level ramp `+0x50c8` | fixed | the lane-1 target chain's first factor |
| the pan ramp `+0x5148` | ~3% off | one of the four chain factors is still not the one the original multiplies |
| ~~the counters and peaks~~ | fixed | the per-track gate is a byte, and the 1000-block branch |
| the two modulation-block words | 19 and 38 | the tail's master LFOs (slots 8/9)'s shape output, ~0.03% off |
| the group sums | word 9 | one LSB, at group 0's sample 4 |

**The accumulator block is `memset` on every call** (`memset(&DAT_01327a20, 0, 0x400)` at the top of
`Synth::render`): the mix-down sums into it, so the port has to clear it too. `fe55ed7` does that, and
the group sums went from differing at word 0 to differing at word 9 by exactly one LSB. The same
commit fixed the input buffer's address (0x1228aa0, 0x200 bytes - it was pointing at 0x1228220).

Note on the group gain: it is **not** the problem. The earlier "1,024 short" was my decimal
conversion of `0x1a1dc8e`; the device's own computation is `0x842f4 + 0x199999a = 0x1a1dc8e` and the
port's formula gives exactly that.

The track filters' cutoff and level are the layer-0 modulation block's **words 8 and 9**
(`DAT_01328d0c`/`DAT_01328d10` are 0x20 and 0x24 bytes in); the port was passing 11 and 12, so every
filter ran on the wrong parameters. `a9a466c` fixes that, and **the eight track filters and the eight
DC blockers now match word for word**.

The comparison covers everything the loop owns: the setup, the LFO array and its state, the voices and
their engine dispatch, the filters, the blockers, the counters and peaks, and both ramps. Two things
are left in the loop:

1. the two modulation-block words the tail's master LFOs leave (19 and 38, ~0.03% off);
2. ~~the group sums~~ - fixed: the mix-down's first term rides the **advancing** pan lane. The
   original re-reads the ramp's lane 1 at the top of every iteration, before that iteration's step;
   the port used the fixed input value, which absorbs into the truncation for the first few samples
   and then shows as one or two LSBs. With that fixed **every word the track loop owns matches**.

So the whole track loop is verified: the setup, the LFO array and the reset seam, the voices and their
engine dispatch, the eight track filters, the eight DC blockers, the counters and peaks, both ramps,
the group gain, the mix-down and the two 128-word accumulator groups.

**What is left in the loop** is *one* word, reported twice. Layer 0's word 38 and layer 1's word 19 are
the *same* address - `0x1228cec + 38*4 = 0x1228d38 + 19*4 = 0x1228d84` - because the two modulation
blocks overlap by eight words (layer 0 spans `0x1228cec`..`0x1228d3f`, layer 1 starts at `0x1228d38`).
The port keeps both as offsets into one scratch buffer, so the aliasing is automatic there.

**The write is invisible to three instruments.** In a re-run of the case, `0x1228d84` reads `688567`
before `Synth::render` and `688384` after it, and the write is *not* observed by any of:

* `UC_HOOK_MEM_WRITE` over the range `0x1228d38`-`0x1228e00` (which does catch the LFOs' parameter
  copies and their markers, so the hook and its filter are working);
* a monkey-patched `OpzSo.write` (which the harness's native `memset`/`memcpy`/`memmove` use);
* a monkey-patched `uc.mem_write` (the lowest level available from Python).

**Found, with one instrumentation trap worth remembering.** The writer is a *byte* store in the block
that runs between the track loop and the tail:

```text
0xf88c0: strb w9, [x8, #0xd84]     ; x8 = 0x1228000, so 0x1228d84
0xf88c4: b.ls 0xf88d4
0xf88d0: strb wzr, [x8, #0xd84]
```

Two things kept it invisible. First, **Unicorn reports the *old* value in a byte-sized write hook** -
the write at `0xf88d0` printed `value=0x0`, which reads like "a byte was zeroed" but is actually the
pre-write content; the poll right after it shows `688384`, i.e. the low byte became `0xC0`
(`0xA81B7 -> 0xA81C0`). Second, the block is in the *sequencer-check / input-selector* section that
follows the loop (`*(long *)(&DAT_00346a50 + seq) == seq + 0x3469b0`), which I had assumed v1 never
reaches. It does.

That address is the **overload counter**, `DAT_01328d84`, and the block is the one that decides
whether the mixer is running long enough to kill a voice:

```c
dVar72 = get_time_monotonic();
uVar60 = (long)(dVar72 * 4e8) - (long)(dVar70 * 4e8);      /* two readings inside the same call */
if (*g_renderingSong == 0) {                               /* host flag; zero in v1 */
    if (uVar60 < 0x46cd1) {
        if (uVar60 < 0x40b29) { counter = 0; }
        else { counter += 1; if (counter > 2) goto overload; }
    } else {
overload:
        InstrumentManager::handleOverload();
    }
}
```

The counter is a *persistent byte* in the .bss, which is why the device leaves `0xC0` there: the
fixture's LCG prefill puts `0xB7` in that byte and each block increments it, so the value depends on
how many calls ran before. The port has to model it (a byte at `at(0x1228d84)` in its scratch) and
update it per block, which needs the clock delta as a **host input** - the same `Host::render_units`
that is already declared and unused.

The fixture cannot supply that delta today, because it is a *local* (`dVar72 - dVar70`), not memory.
The clean way is to stub `get_time_monotonic` in `synth_render_fixtures`, record both readings per
case, and have the test pass their difference; then the counter byte is reproducible on both sides.

Polling the word inside hooks that fire during the call *does* bisect it. With polls on the track
loop's head (`0xf7fb8`), the mix-down's store (`0xf8490`), and every `bl` in the tail's FX/master
section, the value reads `688567` at every loop poll - all eight track heads and every mix-down store -
and `688384` at the first tail poll (`0xf99b0`). So the write happens **between the loop's last
mix-down store and the tail's first LFO render**, a window that contains only: the loop's per-track
peaks and the master mix, the first FX pass's `FxManager::render(10, ...)`, its
`trackFilterProcess(0x6b44, &0x12286a0)` and `trackFilterDcBlock(0x6b70)`, its 16-bit peak, and its
three-way accumulate into `param_1`, `0x1227e20` and `0x1228020`.

The three accumulate targets are all *below* `0x1228d84` in the scratch, and `FxManager::render` with
no plug loaded writes nothing at all - so the next poll set is that window's own `bl` sites
(`0xf9840`, `0xf9868`, `0xf9884`, plus the accumulate loop's store), which should pin it to one call.

A read watchpoint is not useful - the code the hooks can see only reads that word.

**Why the watchpoint missed it.** `opzso.py` implements `memset`, `memcpy`, `memmove` and
`__memcpy_chk` *natively* in Python (`so.write` -> `uc.mem_write`), so their writes never go through a
CPU store and a `UC_HOOK_MEM_WRITE` hook cannot see them. The device's unseen write at `0x1228d84` is
therefore a *libc* copy, and a block copy reaching it is easy to find: the shared parameter block at
`0x1228ca0` is 0x150 bytes, which covers `0x1228d84` (word 57 of that block). The port's Voice path
calls `reset_lfo` rather than the device's `Synth::noteOn` parameter-block copy. To catch it, wrap the
harness's own `write`/`mem_write` (a monkey-patched logger) instead of relying on a CPU hook, and log
which libc call and which PC performs it.

**Settled: it is a port bug, and the fixture is faithful.** A re-run of the same case under the probe's
own setup produces a scratch that matches the fixture's recorded values **word for word, all 3651 of
them** - so the harness is not lying, and the device really does leave `688384` at `0x1228d84` while
the port leaves the prefill (`688567`).

The sharp clue is what `688384` is: it is the prefill value of the **neighbouring word** (word 1248,
`0x1228d80`), not a shape value. So the device's content at `0x1228d84` equals the scratch word one
below it, which is what a *block* or *vector* store - or a copy that is off by one - looks like. The
places that write that region are the LFO renders' parameter copy (`out[i] = params[i]` for 18 words,
so not on its own), their `out[dest]` shape writes, and `Synth`'s track-6 copy of the FX parameter
blocks. Hooking the stores in `Lfo::render` (0x13d0b8-0x13d7b8) that land in `0x1228d38`-`0x1228e00`
is the next step, and a watchpoint that missed the write once already needs a broader filter. Both blocks match everywhere else, and an LFO's
shape value depends on the destination word's *prior* content, so the cause is a write the final
content has already overwritten. Hooking the LFO renders of the writes in between is the way in.

**The group gain's formula, confirmed from the disassembly** (`0xf7d44`-`0xf7d64`):

```text
w10 = 0x199999a                       // the addend
mul x9, x9, x20                       // x20 = 0x0CCCCCD0, set at 0xf7b40/0xf7b50
lsr x9, x9, #31                       // logical
adds w9, w9, w10                      // saturating
stur w9, [x29, #-0x28]                // local_88[0], a stack slot
```

so `sat_add((input * 0x0CCCCCD0) >>u 31, 0x199999A)` is right, and the remaining 1,024 is in the
**input**: the device's value implies an input of `5,425,506` while the recorded folded `+0x684c` is
`5,414,283`, so the register feeding the multiply (`w9` at `0xf7d44`) does not hold the folded
`+0x684c`. Note that the branch two instructions earlier (`0xf7d40`) tests the *current* fold (`w10`,
the `+0x6858` one), which means the compiler kept an earlier fold in `w9` across the three later ones.
The next step is to hook `0xf7c40`-`0xf7d44` and watch `w9` - the same trace that settled the lane-1
chain.

The measurement, for the record: for `filled` track 0 the device's `local_88[0]` at the gain multiply
(`0xf83f8`) is `0x1a1dc8e = 27,385,998`, and the word it comes from - the *folded* `+0x684c`, which
the fixture records - is `5,414,283`. The formula is `sat_add(mul31(folded * 0xcccccd0), 0x199999a)`
with `0x199999a = 26,843,546`: that gives `541,428 + 26,843,546 = 27,384,974`, i.e. exactly **1,024
short** of the device's value, so the term should be `542,452` and one of the constant, the shift or a
missing addend is still off. (Both `0xccccccd` and `0xcccccd0` give the same term, so it is not the
low nibble.) Hooking the setup's own instructions (`0xf7...`, the lines that write `+0x684c` and then
`local_88`) is the direct way to read the constant and shift, the way the lane-1 chain was settled.

outright - the four factors are the four *independent* saturating complements, chained

| `w22` | `0x7fffffff - mul31(mute * this[+0x6c48])` |

The words *before* those match, so the LFO phase (both layers, including the reset seam) and the

**The modulation blocks are the next blocker, and they are the tail's doing.** Layer 1 matches words
0..18 and differs at word 19; layer 0 differs from word 0 on. That is not the loop's LFOs - the
device's own parameter region (0x51c8..0x6860, which includes every smoothed block the LFOs are given
as parameters) matches word for word. It is the FX/master section, which renders three more LFOs -
slots 8, 9 and 10 at `+0x4e60`, `+0x4e8c` and `+0x4eb8`, with the parameter blocks at `+0x5d08`,
`+0x5d50` and `+0x5e70`, and hands them `&DAT_01328cec` (layer 0) as their output. They run at C lines
2755, 2812 and 2283, so *after* the track loop, and nothing downstream can match until that section is
ported.

That section (C lines 2690-2870) is: `trackFilterDcBlock(this + 0x6b70, mix, 0x12288a0)` for the
master track, the three LFO renders, four `FxManager::render` calls (no-ops in v1), the three
FX-track mixes each through its own `trackFilterProcess` and `trackFilterDcBlock` into 0x12288a0 and
then added into `param_1`, and the master DC blocker that moves `param_1` into 0x12288a0 for
`bounceAudio` and the compressor.

**`+0x174` is solved, and it is a layout fact, not an arithmetic one.** A write watchpoint on voice
0's `+0x174` shows exactly one write in the whole call - `Voice::renderVoice`'s store at `0x13dbcc` -
and the value it writes is `0xff3bb6c2`, which the *device's own* `centsDetune` table reproduces
exactly: `table[225] * centsDetune[0] >> 30 & ~1` with the table's element 0 equal to **6449518**,
not the `0x20000000` the port computes. The reason is that on the device the two modulation blocks
*overlap the head of `Tuning::centsDetune`*:

```text
layer-0 block   0x1228cec   (0x54 words = 0x150 bytes → 0x1228e3c)
layer-1 block   0x1228d38   (0x54 words = 0x150 bytes → 0x1228e88)
Tuning::centsDetune  0x1228d88   (2401 words → 0x122b30c)
```

`centsDetune` starts 0x50 bytes into the layer-1 block's 0x150, so an LFO writing `out[dest]` with a
high destination - or even the marker at `out[18]` - *is* writing the detune table. That is real
device behaviour on the voice path, and it is reachable in v1 whenever a modulation parameter selects
a high destination, so the port has to reproduce it rather than compute `centsDetune` into a private
static.

The fix, and it is small: the voice path should take the detune *value* (`cents_detune_at(index)` is
still the right helper for callers whose table is not aliased), and the mixer must take it from its own
scratch - which therefore has to span `0x1227a00` through `0x122b30c` (3651 words), with the table at
word 1250. `VoiceHost.detune_index: u16` becomes `detune: i32`; the voice and manager fixtures pass
`cents_detune_at(case.detune_index)` as they do today.

The older, still-valid part of the analysis:

The `+0x174` diff is precise and surprising: for a voice whose every other field matches (note,
variant, the ADSR words, the step at `+0x17c`, the bend and vibrato, the legato byte, and both the
current frequency at `+0x170` and the previous one at `+0x178`), the port's target is
`note_frequency(note, variant < 4, centsDetune[0])` while the device's is a value that is **not**
`table[note] * detune >> 30` for any table entry or any `centsDetune` entry (implied detunes come out
at 0.003 of full scale, and the table's whole range is 0.5 to 1.0). `Voice::renderVoice` does store
exactly `(table[note] * detune) >> 30 & ~1` at `+0x174` (0x13dbcc), so something writes it
afterwards - the fresh path of `Voice::noteOn` stores the *same* value at both `+0x174` and
`+0x178`, and the legato path does not touch it. The next thing to check is which of `renderVoice`'s
callers can overwrite it, and whether the fixture's voice went through `noteOn` at all. The three send buffers are not compared: their gains are the one part of the
preamble's `mul31` chains that is not decoded yet.

The test's own machinery, worth keeping: it rebuilds the `Synth`'s structured parts (23 LFOs, 13
filters, 12 blockers, 44 voices) from the fixture's word buffer, runs the loop, writes the objects
back into the words, and compares only the regions the loop owns - with the port's deliberate gaps
masked on *both* sides (the engine area, the three entry points, the engine's state block, the bytes
the original's constructor leaves untouched).

## The seam decisions a resuming session must not undo

* **`EngineVoice` (in `voice.rs`)** replaces the original's three per-voice function pointers
  (`+0x08` render, `+0x10` noteOn, `+0x18` noteOff). `InstrumentManager::render` should call
  `Voice::render_voice`, and the engine's state block at `+0x58`..`+0x16f` belongs to the engine.
  `SynthHost::reset_lfo` is the same kind of seam for the `g_synth` global that `Voice::noteOn`
  reaches.
* **Host values are arguments, never globals**: `VoiceHost { detune_index, auto_legato_glide,
  last_note }` (the sequencer's `centsDetune` index, `g_autoLegatoGlide`, `Voice::s_lastNote`).
  `masterCompressor` takes its whole state in `MasterCompressor`. `Lfo::render` takes `bpm`, `pitch`
  and `pitch_dz` in place of `Sequencer::getBPM` and the two accelerometer globals. Keep going that
  way: the chain owns one of each.
* **Embedded tables are generated**: `tools/gen-lfo-tables.py` and `tools/gen-voice-tables.py` read
  the `.so`; both have a `--check` mode. `Tuning::centsDetune` is the exception - it is `.bss` that
  `initTuning` computes, so `tuning.rs` computes it and the fixture checks all 2 401 words against the
  original's own output (the harness stubs `exp2`).
* **The ADSR types are still split**: `adsr::Adsr` (six words, the device's layout),
  `digital::DigitalAdsr` (four fields) and `sample_player_gain::Adsr`. The wired chain will need one
  of them as canonical, with adapters at the `EngineVoice::render` boundary - the engines update the
  level per frame, so the adapter must copy the four shared fields back.

## Fixture technique worth reusing

`make_host_fixtures.py`'s `voice_fixtures` writes Python stubs over the original's function pointers
(found with `opzso.stub_address`) and records the registers each stub was called with. That pins a
function whose callees are engines without pulling the engines in. Two traps already paid for:

* The three pointers are 8 bytes wide - write them with `write_u64`, and zero *both* halves of each
  slot in the recorded words or the stub address leaks into the comparison.
* Register arguments are easy to get backwards. `Voice::renderVoice` is `(this, out, params)`, and a
  fixture with `out` and `params` swapped silently pins the wrong thing - it cost two debugging
  rounds before the glide cases made sense. Check a call's argument order against the C *and* the
  disassembly before trusting a fixture that "fails oddly".

## Measured facts about the remaining pieces

* `Synth::render` is the global mixer. Its per-track work is: `Lfo::render` twice (or once) per layer,
  `InstrumentManager::render` twice (layers 0/1), `trackFilterProcess`, `trackFilterDcBlock`; then
  `masterCompressor` and `bounceAudio` over the master block.
* The mix buffers are library `.bss` scratch, 0x200 bytes apart: `0x12284a0`, `0x12286a0`,
  `0x12288a0`, plus `0x1228cec`/`0x1228d38` (small, and near the shared parameter block at
  `0x1228ca0`). The port must own them rather than reach for statics.
* `trackFilterProcess`'s tables are indexed `bank * 0x104 + row * 4` bytes - **0x104, not the 0x924
  between one table and the next**. Both indices read below the table (mode to -16, row to -64), so
  `filter_tables.rs` carries that padding.
* The filter's ramp flag does not only enable a pass: it *replaces* the value the state's cutoff word
  ramps toward with `(0x1fffffff - cutoff)` (zeroed when negative) `<< 2`, before anything else reads
  the parameter. The row weight still uses the original `(cutoff & 0x1ffffff) << 6`.
* `Synth::resetLfo(this, track, layer, params)` resets the LFO at
  `this + track*0x2c + layer*0x1e4 + 0x4d00` with the parameter block at
  `this + track*0x48 + layer*0x480 + 0x5ac8`, and repeats the first one when `layer == 1` and
  `[g_sequencer + 0x1c] == 0`. The LFO array's layer stride is *eleven* slots, so slot 11 is both
  track 11 of layer 0 and track 0 of layer 1.
* One `Lfo` is 0x28 bytes of state inside a 0x2c-byte slot: `+0x07` and `+0x1e`..`+0x1f` are bytes no
  LFO path touches, and a byte-exact port carries them anyway.
* The random value comes from one library-wide LCG (`randSeed`, shared with `AnalogA`'s noise), so
  `Lfo` takes `&mut seed` rather than owning one. The chain must own exactly one and hand it to both.
* `Synth` is at least 0x6d2f bytes (the mute byte at `+0x6d2e`); the harness allocates 0x7000.
* `InstrumentManager` owns 44 voices at a 0x190 stride; `Voice::s_lastNote` (16 bytes) is at
  `0x16e8b48`, `g_autoLegatoGlide` at `0x1de770`, `g_synth` at `0x1227798`,
  `Tuning::centsDetune` at `0x1228d88` (2 401 words), `g_bouncingAudio` at `0x12322a0`,
  `bounceWritePos` at `0x1232298` and `bounceBuffer` at `0x122de98`.
* `tools/resolve-got.py <slot>...` resolves a GOT slot to its symbol and address from
  `.rela.dyn`/`.rela.plt` - that is how the globals above were found (`python3 tools/resolve-got.py
  0x1d58f0`).

### The `silent` case (the last whole-mixer case left)

13 of the 14 whole-mixer cases match, including all six clock cases. `silent` - the all-zero-state
case - differs in the LFO array, the per-track `+0x68b4` byte and both modulation blocks, and the diffs
point the same way: the port takes the "voices rendered" branch and the device takes the "nothing
rendered" one.

* `+0x68b4` (written when a track's manager pass rendered *no* voice) is `1` in the device and `0` in
  the port.
* The LFO phases differ by a factor: the device advances to `0xBD60000`, the same value the `filled`
  case reaches, while the port's is `0x52D8A800`. `filled` and `silent` are handed different
  parameters, so identical device phases suggest the device's silent run is not using the parameters
  the port thinks it is.

Measured further, and the contradiction is sharper than a branch reading:

* with the `silent` inputs a probe run calls `Voice::renderVoice` **38 times** - exactly 19 voices on
  each of the two layer passes, i.e. every voice in the bank - so the device *does* render;
* and the fixture's `changed` list for that case shows the per-track byte set to `1` at
  `0x68b4`, `0x68e0`, `0x690c`, `0x6938`, `0x6964`, `0x6990` and `0x69bc` - tracks 0..6 and *not*
  track 7 (so the track with the largest bank is the one that does *not* get the byte);
* the filled cases pass with the port's current `voices == 0` condition, so the condition cannot
  simply be inverted.

`+0x68b4 + track*0x2c = 1` and a full render therefore hold at the same time on the device, which the
C's `if ((char)local_a0 == 0) { *pSVar2 += 1; this[...] = 1; }` cannot produce if `local_a0` is the
manager's rendered-voice counter. The next thing to check is what `local_a0` actually is at that
point in the disassembly (`0xf8190`-`0xf81bc`) - and note that both paths write the *same* halfword
(`*pSVar2`), one incrementing it and one zeroing it, so the byte and that counter may be tracking
different things than the C's naming suggests. Either the device's manager test is not the one the port implements (the manager fixture used a
spec with explicit sounding voices, so a "note byte equals something else" condition could hide
there), or the silent case's Synth is not the all-zero one the test builds.

### The `silent` case, continued

Two things closed it further:

* **`+0x68b4 + track*0x2c` *is* the track filter's own `+0x28` rescan byte** - the filters start at
  `0x688c` with a `0x2c` stride, so track `t`'s filter `+0x28` lands on exactly that address. The port
  modelled a separate "silence marker" and wrote the byte directly, which the test's filter write-back
  then clobbered; writing it through `TrackFilter::reset` fixed the marker diff.
* The disassembly at `0xf8160` shows the write exists in the *other* arm too: a track that **rendered
  but is not enabled** (its `+0x6d1c` byte clear) marks itself rather than running its filter. That is
  implemented now.

Left in the case: the LFO phase, and it is **exactly 7x** - the port's step is 1 390 018 560 and the
device's 198 574 080, and the device's number is `256 * 120 * 0x1940`: a rate-table entry of 256
against the port's 1792, with the same tempo. So the two runs disagree about the rate index (or the
tempo), even though both are handed `params[14] == 0` in this case - which points at the smoothed
parameter block rather than the rate arithmetic.

### The `silent` case: the LFO phase is a *count* of renders

The 7x is not a rate error: the device's `RATES` are `[256, 128, 64, 32, 16, 8, 4, 2]` and the
generated table matches, so `256 * 120 * 0x1940 = 198 574 080` is exactly what `RATES[0]` gives at
120 BPM. The port's phase is **seven times one step**, and seven is the number of LFO renders slot 0
takes in that block: one from the track loop plus one per voice re-trigger through `Synth::resetLfo`.
So the port's renders *accumulate* and the device's do not.

`Lfo::reset` re-arms (zeroing the phase) only when `params[16] >> 30 != 0`, and `render` re-arms when
the LFO's own `enabled` byte is set. In the `silent` case the smoothed block is all zeros and the
`enabled` byte is zero, so neither gate should fire and both sides should accumulate - yet the device
ends one step after zero. That is the thing to check next: hook `Lfo::reset` and the rearm inside
`Lfo::render` (`0x13d0d0`-`0x13d184`) during a re-trigger and see which gate actually fires, rather
than trusting the two conditions as read.

### The track loop matches: `Synth::render`'s loop is verified

`9968d3d` un-ignores `synth_render_tracks_match_the_original`. All **14** whole-mixer cases pass,
comparing every word the track loop owns:

| verified | |
|---|---|
| the setup (interpolate + the four master words + the pan complements) | ✓ |
| the LFO array, its state, the reset seam | ✓ |
| the voices, their records, the engine dispatch | ✓ |
| the eight track filters, the eight DC blockers | ✓ |
| the counters and peaks, the overload counter | ✓ |
| both per-track level and pan ramps | ✓ |
| the group gain, the mix-down, both 128-word accumulator groups | ✓ |

The last two blockers were plumbing rather than arithmetic, and both are worth remembering:

1. **`g_synth` was never set by the whole-mixer fixture**, so every voice re-trigger reset an LFO at
   address zero plus the offset while the Synth's own LFOs only took the loop's single render. The
   voice fixtures set it; this one did not.
2. **The second LFO reset is gated on the sequencer byte at `+0x1c`**, which the test hard-coded to
   zero instead of passing the fixture's `playing` flag. Slot 1's re-triggers all come from voices
   whose pins give layer 1, which is what made the gate visible.

Harness traps found on the way, both able to waste a session:

* running the host test with `SYNTH_RENDER_DEBUG=1` **skips the assertions** (the debug path
  `continue`s), so a green result under that variable means nothing;
* `memset`/`memcpy`/`memmove` are implemented natively in `opzso.py`, so their writes are invisible to
  `UC_HOOK_MEM_WRITE`; and Unicorn reports the *old* value in a byte-sized write hook.

What the test deliberately does not look at: the three send buffers, the four output blocks and the
master tail - those are unported, and the sends' gains are still undecoded.

### The tail and the master bus: ported, converging on the master's DC block

Two corrections the comparison forced, both measured on the device:

1. **The mix-down's sixth destination is the track mix at `0x12286a0`.** The body's last store is

   of the eight passes with a `UC_HOOK_CODE` hook at `0xf8428`, matching the port's gated module gain.
   The port had been throwing that term into a private local.
2. **That slot is the *input* of the tail's track-10 filter** (its `FxManager` destinations are the

**Next:** the master's DC-blocked mix at `0x12288a0` - its input is `param_1` after the tail's three

### The tail's filters: FX 9's state is the one that differs

Adding the tail's own filters and blockers to the comparison (the region `0x6abc..0x6c00`) surfaced the
next concrete diff, and it is *not* the master bus:

| case | word | port | device |
|---|---|---|---|
| `filled` (and every LCG-filled case) | `+0x6b00` | `-2172764` (the LCG prefill, unchanged) | `9307` |
| `silent` | `+0x6bdc` | `0` | `1664` |

`0x6b00` is **FX track 9's filter** (`0x6abc` is track 8's, `0x6b00` track 9's, `0x6b44` track 10's).
Its state holds the prefill in the port, so the port's FX-9 filter is not writing its state while the
device's is. FX 8's filter (`0x6abc`) *does* match, which rules out the pass being absent and points at
the second iteration of the tail's modulator/FX loop.

The two passes' arguments, read from the assembly (`0xf99f0`-`0xf9a44`):

```text

trackFilterDcBlock(this + 0x6ae8, x24, 0x12288a0)
```

so the port's shape (`FX_MIX` in, `MOD_LAYER0 + 8/+9` as the parameters, `0x12288a0` out) is right; the
difference has to be in where the second iteration's state goes.

Also confirmed this round, from the same assembly:

* **the master's filter parameters are `this + 0x5e00` and `this + 0x5e04`** - the address register

The comparison itself was the real weakness this round: the broad region list only *printed* its

### The tail is verified; the compressor's references are the last thread

`df4e32a` closes the tail's filter question and takes the whole `Synth::render` to a single
one-LSB difference in the master's output block.

**The FX passes filter the FX mix in place.** The FX-8 filter's output buffer *is* the FX mix
(`trackFilterProcess(this + 0x6abc, 0x12282a0, ...)`), so the FX-9 pass reads what the FX-8 pass wrote.
The port filtered a local copy and left the FX mix raw, which is why FX 9's filter state kept the fill.
Translated into the port as one write-back, all four tail filters and all four tail DC blockers match.

**The master gain chain, instruction for instruction** (`0xf9ea0`-`0xf9fcc`, and the volume pass at
`0xfa4c0`):

```text
x10 = (u64)(this[0x6858]^2) >> 31                 ; lsr, so the narrowed square is its low 32 bits
x10 = (signed)((i32)x10 * 0x5fffffff)             ; smull, then `lsr x10, x10, #31`
x10 = (square == 2^62) ? 0x5ffffffe : x10         ; the non-standard sentinel
gain = sat_add(x10, 0x20000000)

per sample:
  x16 = (i64)mix[i] * gain
  x16 = sbfx(x16, #29, #34) & ~3                  ; a 34-bit field: the sign comes from bit 62
  x16 = clamp(x16, -0x80000000, 0x7fffffff)
  sq  = mul31_arith(x16 * x16)                    ; sentinel 0x7fffffff
  cub = mul31_logical(sq * x16)                   ; sentinel 0x7fffffff
  x17 = sat_add(x16, sat_sub(x16, cub) >> 1)      ; asr #1
  out = sat_add(mul31_logical(x16 * dry), mul31_logical(x17 * wet))
  peak = max(peak, out)                           ; stored as a halfword at this + 0x6c34
volume pass:  out = min(0x7fffffff, mul31_arith(this[0x6860] * out))
```

The port's earlier form differed in three places (`*2 >> 0x1e` instead of the 34-bit `sbfx`, a
`-0x7fffffff` lower clamp, the blend written into the scratch) and now matches the assembly.

**Verification state.** The comparison asserts, for all fourteen cases: the setup, the LFO array and its
state, the voices and their engine dispatch, the eight track filters and eight DC blockers, the tail's
four filters and four blockers (exact spans, not the unmodelled gaps between them), the counters and
peaks, both ramps, the group gain, the mix-down, both accumulator groups, the modulation blocks, and
every scratch word the device changed except the sends. Only the master's output block and the
compressor's state are still outside the assertions - and since the chain above now matches the
assembly, **the one-LSB output difference points at the compressor's four references**, which is the
next thread:

| reference | port reads |
|---|---|
| 1 | `this + 0x6854` |
| 2 | `this + 0x6298` |
| 3 | `sat_add(mul31(this[0x629c] * 0xc8f040d), 0x734ec8aa)` |
| 4 | `sat_add(COMPRESSOR_GAIN[bucket], mul31(((bpm - 40) mod 20 * 0x6666666) * (table[bucket+1] - table[bucket])))` |

Also fixed this round: the tail region first compared `0x6abc..0x6c00`, whose gaps hold bytes nothing

### The master bus's buffer flow, and the one number still open

`56bdd5b` fixes a *buffer identity* mistake that had been hiding inside the master tail. The gain stage and
the scratch at `0x12288a0` are two different buffers, and the port had them conflated:

| buffer | who writes it | who reads it |
|---|---|---|
| `0x12288a0` | the DC blocker of the master (in place), then `masterCompressor` (in place) | the gain stage (`[x20, x12]`) |
| the caller's `param_1` | the gain stage's blend (`str w16, [x25, x12]`) | the volume pass, in place |

The port now copies the DC-blocked mix into the scratch **after** the compressor, puts the blend into the
caller's buffer, and runs the volume as its own pass over that buffer.

Two more things were confirmed with it:

* the parameter region now runs through `0x6864`, so the master volume word (`0x6860`) is compared - it
  matches, which is why the volume pass was never the source of the LSB;
* the compressor's four references were re-derived from the assembly and match the port exactly:
  `this[0x6854]`, `this[0x6298]`, `sat_add(mul31(this[0x629c] * 0xc0f040d), 0x734ec8aa)` and the tempo ramp
  (`COMPRESSOR_GAIN[(bpm-40)/20]` with a `0x06666666`-scaled fraction; bucket 7 above 199 BPM).

**Still open: the master's DC-blocked mix at `0x12288a0`.** Port `-2208924` against the device's
`-2112204` for the `filled` case - about 4.5% - and the output block is one LSB (`2660` against `2659`)
as a result. Since the compressor's references and code are verified, and the input is `param_1` after the
tail's three accumulates, the remaining candidates in order are:

1. the FX-10 pass's contribution to `param_1` - `sat_add(param_1[i], mul31(sample * (0x7fffffff - this[0x5db4])))`
   where `sample` is the DC-blocked track mix;
2. the FX-8/9 passes' plain `sat_add` contributions;
3. the master filter / DC blocker's own state (their state words match, but their output is only visible
   through this one value).

Also verified this round, from the assembly: the tempo ramp's bucket is `(bpm - 40) / 20` by a
magic-number division, `7` above 199 BPM, and the fraction is `(bpm - (bucket*20 + 40)) * 0x06666666`
when that difference is at most 20, clamped to `0x7ffffff8` otherwise.

### The engine seam exists: `EngineVoice for VoiceEngine`

`73c4865`. The ported `Mixer` drives its engines through the `EngineVoice` trait, and the host's three
engines never implemented it - so nothing in the app could drive the ported chain. The adapter is now in
`opz-core/src/engine.rs`, with a test that walks every non-drum track in the factory map, starts a note,
renders a block through the trait and asserts sound *and* an advancing envelope.

Two shape differences it bridges, both worth knowing before the wiring:

1. **The envelope.** The device hands its engine a *pointer* to the voice's `Adsr`; the port's engines were
   written against the four words they actually use (`level`, `mul`, `add`, `phase`). The adapter passes
   those four and takes `level` and `phase` back - which is everything any of the three engines writes
   (`digital.rs:569`, `analog_a.rs:666`/`766`). The `rate` word and the re-arm byte stay with the `Adsr`,
   and `Voice::note_off` already sets the flag before calling the engine, so `note_off`'s `&Adsr` being
   immutable is not a loss.
2. **The host tables.** `AnalogAEngine::render` wants banks, pads and two rate tables; the enum's `Analog`
   variant owns them, so the adapter can reach them. The two rate arguments are the *same* table, as the
   interim host also passes them.

The engine's third argument is the glide input, which the port's engines call `track`; the adapter passes
the mixer's `delta` there and the increment as the phase increment. Velocity narrows to the byte the
device's voice record holds at `+0x3d`.

**What the wiring still needs**, in the order it should be done:

1. `Engine` owns a `Synth` and a `Mixer<VoiceEngine>`, and something programs the `Synth`'s parameter
   blocks from the app's per-track `TrackParams` (18 bytes) through `set_target_parameters`,
   `interpolate_parameters` and `force_parameters_to_target`;
2. note allocation: the device's sequencer picks the voice; the host has to pick the first idle voice in
   the track's range (`InstrumentManager::voice_start_index`) and write the voice record's note/velocity
   (`+0x20`, `+0x3c`, `+0x3d`, `+0x38`), the way the fixture's pins do;
3. per-block host inputs: BPM, the clock delta, the detune index, the module gates and gains, the plug ids
   and flags - all of which `LoopHost` already takes;
4. the master output replaces `Engine::render_block`'s mono fold, and the existing engine tests change
   accordingly: the plan already says the offline render cannot stay byte-identical once the master chain
   is real, and asks for a measured, explained difference instead.

### The parameter bridge is almost in place already

Checked while starting the wiring: `TrackParams` (`opz-core/src/params.rs`) already holds
`values: [u8; PARAM_COUNT]`, "raw bytes as the device stores them", alongside the Q31 `current` and
`target` it hands the engines today. That is exactly what `set_target_parameters(words, track, values,
targets, flags)` wants, and it is where the device does both the byte → Q31 conversion and the glide -
so the wiring hands the *bytes* over and lets the ported `Synth` smooth them, retiring the app's own
`TrackParams::interpolate`.

One addition it needs: a byte-level *target* (`[u8; PARAM_COUNT]`, the preset or UI value) to pass as
the fourth argument. The app's `target` is Q31, which is what `interpolate_parameters` produces, not what
it consumes; `values` and `targets` are both device bytes at that seam (`setTargetParameters`'s
`const unsigned char *`).

The off-track case is already handled by the ported call: a track index at or above 12 smooths all
eighteen parameters rather than the lower twelve.

### The chain exists; it renders, and it is silent

`698e3f8` adds `opz-core/src/chain.rs`: the app's view of the ported path. It owns a `Synth` and a
`Mixer<VoiceEngine>`, assigns each track's voices that track's engine (through the device's own ranges
from `InstrumentManager`, clamped to the 44-voice array - the last track's layer-1 range runs off the end
of it), programs parameters through `set_target_parameters`, starts notes on a track's first ungated voice
through the same reset seam the loop's voices get, and renders a block through the four ported calls. The
master buffer it returns is the device's interleaved stereo one, 128 words.

Two pieces of state the device keeps and a fresh `Synth` does not, now settable:

| word | meaning |
|---|---|
| `+0x6860` | the master volume; zero means silence, so it must be set before anything is audible |
| `+0x5108` / `+0x5188` | the per-track level and pan the ramps at `+0x50c8`/`+0x5148` move toward |

**The end-to-end test is ignored: the chain renders but stays silent.** With the master volume, the
level/pan words and the mute mask all set, the remaining candidates are on the render side, in this
order:

1. **does the voice run at all** - the app's track index is 0-based and every device seam is 1-based, so
   a note started on "track 4" lands on device track 5's range (`TRACK_START[5]` = 10). Worth printing
   the voice's `note` and the engine's call count after a `note_on`, the way the whole-mixer test
   records `ENGINE_CALLS`;
2. **the ramps** - both start at zero and move a 128th of the distance to their target per sample, so a
   handful of blocks should be enough for the level ramp to leave zero; if it does not, the target is
   still the problem (the level target is `+0x5108`, the pan target is the lane-1 chain times
   `+0x5188`);
3. **the fold into the master** - `render_master_mix` reads the two group sums, whose gain comes from the
   folded `+0x684c`/`+0x6850`; both start at the fixture fill on the device and at zero here, and
   `render_setup` only folds them one step per block toward the song byte.

The cheapest next measurement is (1): the whole-mixer fixture's own pins show exactly which voice fields
the device needs before it renders, and the port's `Voice` has them all public.

### The chain was silent for four measurable reasons, and the fifth is the engine's state

`e2f42aa`. Running the chain test with `SYNTH_CHAIN_DEBUG=1` prints the voice's record and the mix's
first sample per block, which localised the silence one layer at a time. Four were *device state a fresh
`Synth` is missing*; all four are fixed:

| missing | how it shows |
|---|---|
| the `centsDetune` table | the mixer's scratch aliases `Tuning::centsDetune`, which the device builds at load. Zeroed, every note's frequency comes out **0** - the detune is a multiplier, not an offset. The chain now seeds it from `tuning::cents_detune()`. |
| the per-track enable byte at `+0x6d1c` | a track that is not enabled never runs its filter and never reaches the mix. This is a *different* gate from the mute mask at `+0x6848`; the level setter now sets it too. |
| the master volume at `+0x6860` | zero multiplies the whole master to zero. |
| the envelope's *level* | the device's `noteOn` writes the envelope's `mul` and phase but not its level, and all three engines scale by the level. The chain arms it the way the interim host did. |

With those, the voice runs: the manager's counter advances each block, `adsr.level` reads `0x7fffffff`,
and `+0x174`/`+0x178` hold note 60's increment (`12 740 058`). The per-track level ramp also moves
(`0x7fffff80` after one block, from the 128th-per-sample glide).

**Still zero: the engine's contribution to the track mix.** `TRACK_MIX` and `TRACK_FILTERED` are both
zero after a block even though the manager rendered the voice, so the engine is either writing zero or
skipping. The next measurement is the engine's own state block (`+0x58`..`+0x16f`, which the port keeps

and the preset supplies the rest, so a fresh zeroed block is the prime suspect. `Chain`'s voices take
their engines from `VoiceEngine::for_track`, and the digital branch sets the octave table and the
wavetable but nothing else.

### The engine sounds; the mixer's hand-off is what is left

`2412ee8`. Two more things, and the diagnosis is narrow now.

**The parameters have to be snapped.** A fresh `Synth` leaves the smoothed block at zero, and
`interpolate_parameters` folds it toward the target one sixty-fourth per block, so a note started right
away plays at a tiny fraction of its amplitude - which is why the engine wrote zero for the first
blocks. The device snaps on a preset load (`forceParametersToTarget`), so `Chain::force_parameters` now
exposes that and the test calls it after setting the track up.

**The engine is not the problem.** With the snap, the engine driven *directly* - `EngineVoice::render`
with the track's smoothed parameters and the voice's increment (12 740 058 for note 60) - writes
`[0, 0, -5511, -2767]`. Non-zero, as expected. Through the mixer it still writes nothing, so the
difference is in what the mixer hands over.

The measurement that settles it, written into the test's ignore note: print the modulation block **where
`render_tracks` builds `params0`/`params1` from it**, not after the whole render. After the render the
tail's own LFOs (slots 8 and 9) have already rewritten that block from the *master* track's parameters,
which is why the earlier print showed zeros and why it was misleading: the engine for a track sees the
block as the *track's* LFO render left it, and that is the value to look at.

If that block turns out to hold the parameters, the next suspect is the gain chain the mix-down uses -
`track_gains`' four complements - since the level ramp does move (`0x7fffff80` after one block) and the
group sums stay zero.

### The ported chain makes sound

`1237ba4`. The chain test runs unignored: program the render loop's track 4, arm it, start a note,
render sixteen blocks - the master buffer carries signal.

**The last blocker was a numbering mix-up, and it is worth writing down because it will bite again.**
Two numbering schemes meet in `Synth::render` and they are *not* the same:

| scheme | who uses it |
|---|---|
| the **render loop's** track index (0..7) | `InstrumentManager`'s voice tables (`voice_start_index`) and the `Synth`'s parameter blocks (`setTargetParameters` writes `SMOOTHED + track*0x48`) |
| the **plug map's** track number (1-based) | which engine a track gets (`VoiceEngine::for_track`) |

The chain had been offsetting *both*, so a note landed on a voice the loop never renders and everything
downstream was zero for that reason alone. The constructor now applies the plug offset only to the engine
lookup; the voice ranges, the parameter blocks and `note_on`/`note_off` all use the loop's own index.

**Everything else a fresh `Synth` is missing**, all found by measurement and all now in `Chain::new` or
the test:

| missing | why it silences |
|---|---|
| the `centsDetune` table | the scratch aliases it; zeroed, every voice's frequency is zero (the detune is a multiplier) |
| the per-track enable byte at `+0x6d1c` | a track that is not enabled never reaches the mix; a *different* gate from the mute mask |
| the master volume at `+0x6860` | multiplies the whole master, so zero is silence |
| the level/pan words `+0x5108`/`+0x5188` | the ramps move toward them; both start at zero |
| the envelope's level | the device's `noteOn` writes `mul` and the phase, not the level, and the engines scale by it |
| a parameter snap | `interpolateParameters` folds a sixty-fourth per block, so a note started straight after a program change plays at 1/64th |

Measurement note: printing the modulation block *after* a whole render is misleading, because the tail's
own LFOs (slots 8 and 9) rewrite that block from the master track's parameters. The block to look at is
the one `render_tracks` builds `params0`/`params1` from, inside the loop.

**What is left for Phase 4** is now only the wiring itself: `Engine::render_block` replaces its hand-rolled
voice loop with a `Chain`, the app programs `values`/`targets` from `TrackParams` (which already holds the
device bytes) plus a byte-level target, and the master buffer replaces the mono fold. The existing engine
tests then change, which the plan anticipates: the offline render cannot stay byte-identical once the
master chain is real.

### The Engine wiring: written, and what it takes to land it

`edadf86` adds pack loading to the chain. Beyond that, the wiring of `Engine::render_block` onto the ported
chain **was written, compiled and then reverted rather than committed red** - the whole change is in this
worktree as `PHASE4_ENGINE_WIRING.diff` (`patch -p1 < PHASE4_ENGINE_WIRING.diff` against `edadf86`), and the
next pass should start from it rather than from scratch.

What it does: `Engine` owns a `Chain` instead of a `Vec<Voice>`; `new` loads the packs, enables every track
at full level and centre pan and snaps the parameters; `program_chain` hands the app's `TrackParams::values`
to `set_track_parameters` (the device does the byte → Q31 conversion *and* the glide, so `values` serves as
both current and target) and sets the master volume; `trigger` and the release call `Chain::note_on`/
`note_off`; `render_block` takes the chain's interleaved-stereo master and folds it to the host's mono.

With it, 27 of 30 opz-core tests pass. The three that do not, and their causes as far as the pass got:

| failing test | what it needs |
|---|---|
| `both_synth_tracks_play_a_note` (track index 4, `analoga.engine`) | the analogue engine's **envelope words** are host state: the interim host wrote `envelope_words()[3] = 0x7fffffff` on every note-on, and without it the engine holds in its filter envelope's attack branch. | `drum_beat_and_synth_line_play_together` | "quarter 3 of the bar is not silent": a release-timing difference. | **the analogue engine's envelope phase** | the analogue voice sustains in one phase and phases 1..4 run out after a block. The app's own host set it on note-on; the ported voice arms phase 1, so the chain sets 5 for analogue voices. |
| **snap the boot presets** | a fresh `Synth` starts the smoothed block at zero and glides a sixty-fourth per block. The analogue engine's amplitude scales by `params[11]` and rounds to zero at that size, so the analogue track was silent until the parameters were programmed *and forced*. The Engine does that once at construction; edits afterwards keep the device's glide. |

**The two failures left are expectations, not obvious port bugs, and both need the device as a reference:**

1. `mute_silences_a_track_without_stopping_it` asserts the block right after a mute is *all* zero. It is
   not - the residual is small (peak 1667 against the unmuted block's thousands) and it drains over the
   next blocks. The suspects are the master compressor's detector ring and the DC blockers' stored
   input, both of which carry past samples on the device too. Either the test renders until they drain
   and then asserts silence, or it asserts a ratio.
2. `drum_beat_and_synth_line_play_together` asserts every quarter of the bar carries energy. Measured
   quarter peaks are **511769, 2907, 24, 0** - the audio dies out across the bar, which is far more than
   a compressor would explain and is worth a real diagnosis. The candidates are the drum voice's slice
   selection per note, the master compressor's detector filling up, and the per-track level ramp (whose
   target is set, but which the earlier chain debug showed moving to `0x7fffff80` and staying).

Measuring either against the device means driving the Unicorn harness with the same pattern and
comparing quarter energies; that is the next step for Phase 4's "measured, explained difference".

### Diagnosing the bar's decay: what was measured and what was not

Chasing the `drum_beat_and_synth_line_play_together` failure (quarter peaks **511769, 2907, 24, 0**) turned up
one useful negative result and one dead end worth writing down so neither is repeated.

**The negative that matters**: a hand-built pack pushed through `Chain::load_pack` renders silence for a drum
note of 36 or 60, while the Engine's own integration pack on the same path does sound (the mute test's first
assertion, "the track sounds", passes on a drum track). So the pack plumbing is right and the silence is in
the *note*: the device's sample player maps the note to a **slice**, and a hand-built 24-slice pack with
notes 36/60 does not land on one. Any future drum-side differential test should take its note values from the
app's own pattern defaults rather than picking them.

**The open measurement**: the quarter-energy decay itself. It is not yet localised, and the two candidate
mechanisms need different evidence:

1. the **master compressor's detector** filling across the bar - visible by printing the compressor's state
   (or the gain it applies) per block;
2. the **per-track level/pan ramps** - both are read at the mix-down and both start at zero, so a target
   that is only set once may leave them somewhere other than full scale.

The device is the reference for whichever it turns out to be: drive the Unicorn harness with the same
sixteen-step pattern and compare quarter energies, the way the whole-mixer fixture compares the render word
by word. That comparison is what Phase 4's acceptance asks for ("the offline render cannot stay
byte-identical ... expect a measured, explained difference instead"), and it is the last thing between the
current state and a wiring that can be committed.

The wiring patch (`PHASE4_ENGINE_WIRING.diff`) is unchanged by this round and still passes 29 of 31
opz-core tests when applied.

### The bar's decay: it is the voice side, not the master

Driving the wired `Engine` with a per-block print of the mix's stages (the level and pan ramps, the track
mix, the group sums and the staged mono output) localised the `drum_beat_and_synth_line_play_together`
failure. Sampling every 64th block across the bar:

```text
block  64: ramp L 0x7fffff80  P 0x3f7f7f00  sums 35384525  staged 117147
block 128: ramp L 0x7fffff80  P 0x3f7f7f00  sums 42584915  staged  40972
block 192: ramp L 0x7fffff80  P 0x3f7f7f00  sums    90304  staged  50257
block 256: ramp L 0x7fffff80  P 0x3f7f7f00  sums     1616  staged   4168
block 320: ramp L 0x7fffff80  P 0x3f7f7f00  sums        0  staged   4486
block 384: ramp L 0x7fffff80  P 0x3f7f7f00  sums        0  staged    309
```

Two things this settles:

1. **The ramps are not the problem.** The level ramp sits at `0x7fffff80` (full scale minus the last step)
   and the pan ramp at `0x3f7f7f00` from the first sampled block onward, so both have reached their
   targets and stay there.
2. **Neither is the master.** The *group sums* - what the mix-down accumulates from the tracks - fall to
   **zero** by block 320, which is well before the second kick fires (step 4 is block ~344 at 86 blocks per
   step). The small non-zero `staged` output after that is the tail's own FX path, not the tracks.

So the later kicks never reach the mix at all: the failure is on the voice side. The candidates, in order:

1. the **host's note bookkeeping** in `Engine::trigger`/`render_block`: one `notes[track]` per track, released
   when its frame count runs out, and the *same* voice re-used for the next hit. If the release leaves the
   ported `Voice` gated (`+0x35` non-idle) or the next `note_on` lands on the wrong voice, the hit is lost;
2. the **`Chain::note_on` voice choice** - the first voice whose `gated_note` is idle in the track's range;
3. the **drum engine's slice selection** - the earlier hand-built-pack experiment showed a note that does not
   map to a slice renders nothing, and the same is true of a re-trigger if the engine's per-note state is not
   reset.

The measurement to run next is the one the diagnostic was reaching for: print the voice's `note`,
`gated_note`, `adsr.phase` and `counter` at the sampled blocks. `counter` advancing means the manager
rendered it; `note` still holding the old hit means the trigger never arrived; `gated_note` non-idle means
the release did not open the gate.

### The bar's decay: the drum voice goes constant

The voice-level measurement named in the previous note has been run. Printing voice 0 (track 0, the kick) and
the host's note bookkeeping every 64th block across the bar:

```text
voice 0: note 48 gated 0xff phase 1 counter  64 engine_prev 512   host notes None
voice 0: note 48 gated 0xff phase 1 counter 320 engine_prev 512   host notes None
voice 0: note 48 gated 0xff phase 5 counter  40 engine_prev 512   host notes None   <- re-triggered
voice 0: note 48 gated 0xff phase 5 counter 335 engine_prev 512   host notes None
voice 0: note 48 gated 0xff phase 5 counter  55 engine_prev 512   host notes None   <- re-triggered again
```

What this rules out, and what it leaves:

* **The triggers arrive.** The counter resets (`320 -> 40`, `335 -> 55`) exactly where the kicks fall, the
  gate byte stays idle (`0xff`), and the manager renders the voice every block (the counter advances by 64
  between samples). So neither the host's note bookkeeping nor `Chain::note_on`'s voice choice is losing the
  hit.
* **The voice's frequency is 512** (`engine_prev`), which is `0x400` - the fixed drum scale factor for an
  entity below 4 - times a detune of one half. This is early in the chain: it is the *voice's* record, and
  the sample player may well ignore it, but it is the one field in this record that is obviously not
  note-like.
* **What is left** is the drum engine's own output. The group sums fall to zero while the counter keeps
  advancing, which is the signature of a *constant* (DC) contribution being removed by the track's DC
  blocker, or of a slice that has run to its end and is never rewound. The next measurement is the engine's
  own state across two successive hits - the sample position and the slice bounds after `note_on` the second
  time - which the port keeps inside `DrumEngine` (`state_fields()` exists for exactly this).

Note also that the earlier hand-built-pack experiment and this one agree: a drum voice whose note does not
land on a slice renders nothing at all, and note 48 with a 24-slice pack is a candidate for that. The app's
own `initial_values`/`programmed` defaults give note 48 for a drum step, so if the mapping is
`note - 36` or similar, the port's slice lookup is the first thing to check.

### Correction: the drum's slice lookup is not the problem

The previous note's last paragraph guessed that note 48 against a 24-slice pack might be the drum silence.
That is refuted by the code: `DrumEngine::slice_for_note` is

```rust
let idx = (note as i32 - NOTE_BASE).max(0) as usize;
Some(idx.min(self.instruments.len() - 1))
```

- it clamps to the last slice, so any note finds one, and it returns `None` only when no pack is loaded at
  all. Note 48 against a 24-slice pack therefore selects a slice, as does note 60.

What is left, sharper than before:

* the triggers arrive (counter resets at every kick), the gate is idle, the manager renders the voice every
  block, and the sample player **ignores the voice's frequency** (its `render` takes only `out` and
  `params`), so the odd `512` in the voice record does not matter;
* the **first** hit does sound - `mute_silences_a_track_without_stopping_it`'s first assertion, "the track
  sounds", passes on a drum track - and the bar's first quarter carries the energy;
* the **later** hits do not. `DrumEngine::note_on` resets its position and its envelope word (`self.s0c = 0`,
  `self.s38 = 0x7fffffff`) before setting up the new slice, so the re-trigger path itself looks right.

So the next measurement is inside `DrumEngine::render` for a *second* hit: the sample position at the end of
the previous slice, the slice bounds after the new `note_on`, and the playback step it computes. The voice's
`octave` for note 48 is `(48 + 19) / 24 - 3 = -1`, i.e. the step is halved, which is the one arithmetic
input that differs between hits only through the note - and all four kicks use the same note.

### Root cause found: a drum voice's second hit is deferred forever

The drum engine's own `state_fields()` across the bar, sampled every 16 blocks, shows the position running
away monotonically and never rewinding:

```text
b16  sums   483372  position  40960  sample_frames 768  window 96..608  active 1
b48  sums   783444  position 122880  sample_frames 768  window 96..608  active 0
b96  sums  1306984  position 245760  ...            active 0
b160 sums   653680  position 409600  ...            active 0
```

(`position` advances 2560 per block, so by the end of the bar it is 533 times the slice length.) Every later
kick re-uses that same engine state, which is why the group sums die after the first hit.

**Why the engine's `note_on` is never called again**, read straight out of the port (`voice.rs:375`):

```rust
if self.adsr.phase != 0 {
    // Sounding: remember the note and start it when the envelope ends.
    self.gated_note = note;
    self.pending_note = (velocity & 0xff) as u8;
    self.adsr.phase = 5;
    return;                       // <- the engine's note_on is not reached
}
```

That is the device's *gated* path: while the envelope is still sounding, the note is remembered and played
when the envelope ends, by `renderVoice`'s re-trigger. It is right for the synth engines, whose envelopes run
out. A **drum voice's envelope is the engine's own** (`sample_player_gain` keeps `adsr_level`, `adsr_rate`,
`adsr_inc`, `adsr_phase` in its own state, as the dump shows), and nothing brings the *voice's* `+0x50` phase
back to zero - so the first kick leaves `phase = 5` and **every** later kick takes the deferral branch.

This also explains why the interim host's drums worked: it called the engine's `note_on` directly on every
note and armed the envelope itself, never using the ported `Voice`'s deferral.

**A first fix was tried and reverted**: in `Chain::note_on`, clearing `adsr.phase` for a drum voice whose
`gated_note` is set, so the render's re-trigger picks the note up. The position still never rewound and the
opz-core pass count fell from 29 to 28, so it was wrong in a way the dump does not yet show. The next step is
to confirm which branch `renderVoice`'s re-trigger takes for a drum voice - in particular whether
`pending_note`/`pending_vel` (not `note`) are what it plays, and whether the drum engine's `note_on` is
reached from there - with the same `state_fields()` dump taken across a *single* re-trigger rather than every
16 blocks.
