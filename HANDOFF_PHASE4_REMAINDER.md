## `Synth::render`: the port plan the decompilation supports

The Ghidra C (`analyzeHeadless /tmp/ghidra-p4 p4 -process libSnakePlugin.so -noanalysis`, filter
`Synth::render`) is 2 350 lines and usable once the register noise is skipped. Its shape:

1. **Setup** (C lines 1260-1700): `memset` a 0x400-byte scratch at `this + 0x288`, zero a 0x200-byte
   scratch at `this + 0x688`, then read the plug flags (`PlugManager::getPlugFlags` twice), the module
   sends, the active track, the input selector, the BPM four times, and `get_time_monotonic` twice.
2. **The track loop** (`do { } while (track != 8)`, C lines 1700-2070): for every track 0..7
   * track 6 is the FX/master slot: the parameter blocks at `+0x5c78`..`+0x5c90`, `+0x60f8`.. and
     `+0x5c98`.. are copied into the scratch and two scratch words are set to `0x3fffffff`;
   * otherwise two `Lfo::render` calls: layer 1 at `this + track*0x2c + 0x4ee4` with the block at
     `+0x5f48` and out `this + 0x15a0`, then layer 0 at `+0x4d00` with the block at `+0x5ac8` and out
     `this + 0x1554` (both LFOs take `this + track*4 + 0x6ca4` as an input);
   * two `InstrumentManager::vibrato` calls, on `clamp(this+0x15a0's first word + 0xc0000001) << 1`
     and on `clamp(this+0x1554's first word * 2 - 0x7ffffffe)`;
   * zero the 0x200-byte mix buffer at `this + 0xf08`, then `InstrumentManager::render(track, 0, mix,
     this + 0x1554, &counter)` and the same for layer 1 with `this + 0x15a0`;
   * a per-track halfword counter at `this + track*2 + 0x6aac` and a per-track value at
     `this + track*4 + 0x5108`, and the mix-down into the accumulation buffers at 0x1227a20/0x1227e20
     (four track groups of 0x200 bytes) plus the scratch at 0x1228020/0x12284a0, with the layer-0/1
     modulation blocks at 0x1228cec and 0x1228d38 handed to the voices as their parameter block;
   * the four `FxManager::render` calls, five `trackFilterProcess` and six `trackFilterDcBlock`.
3. **The master tail** (C lines 2070-3610): `bounceAudio`, the four `Sequencer::getBPM` reads, the two
   `masterCompressor`-style blends over the mix buffers at `this + 0xee8`/`0xf08`/`0x1108`, the VU
   words, and the writes into the four output buffers the caller passed.

The scratch the function touches is **not** inside the object: the mix buffers and the modulation
blocks are separate `.bss` objects addressed absolutely - 0x1227a20 (0x400, `memset`), 0x1227e20,
0x1228020, 0x12284a0, 0x12286a0, 0x12288a0, 0x1228aa0 (`inputBuffer`), 0x1228cec and 0x1228d38 - so
the port owns one buffer spanning 0x1227a00..0x1228e00 (0x1400 bytes, 1 280 words) and indexes it by
device offset, while the `Synth` object itself stays wherever its owner puts it. (An earlier reading
of these as `this + 0x288` and friends was wrong: `memset(&DAT_01327a20, 0, 0x400)` would have wiped
the voice array at `this + 0x480`, which the device plainly does not do.)

The fixture is already in place: `synth_render_fixtures` in `make_host_fixtures.py` keeps the object
in an allocation and the scratch in the library's `.bss`, stubs one engine render for all 132 voice
slots - the stub *fills* the engine's block from the increment, so the mixer has signal to scale -
and records 8 cases. `synth_render_fixture_is_alive` in `host.rs` checks it drives the real thing
until the port can replay it.

`Synth::render`'s signature is `(fract32_t *a, *b, *c, *d)`; the four blocks are the main output
plus the two FX returns and the sidechain the master compressor reads.

### What `Synth::render` does, in the order the C shows it

Measured from the decompilation (line numbers are the C's), with the **v1-reachable** path marked; the
input-signal, sampling, tone-mode and song-mode branches are gated on host flags the clone fixes at
zero, so they are documented rather than ported (the plan's `PORT_METHOD.md` rule).

1. **Setup** (1 500-1 700): `mutex_lock(this + 0x6864)`, `interpolateParameters`, then four master
   words at `+0x684c`/`+0x6850`/`+0x6854`/`+0x6858`, each folded one step toward a byte the song
   fixture carries (`master_params[0..4]`, the same 64th-order IIR `interpolateParameters` uses);
   `get_time_monotonic`; the module's two plug ids (`+0x60`, `+0x6c`) through
   `PlugManager::getPlugFlags`; `*(u64 *)(this + 0x6c40) = [0x7fffffff - *(u32*)(this+0x5d38),
   0x7fffffff - *(u32*)(this+0x5d80)]`.
2. **The track loop** (1 700-2 070), eight iterations, all reachable:
   * track 6 skips the LFOs and copies the FX/master parameter blocks (`+0x5c78`, `+0x5c80`, `+0x5c88`,
     `+0x5c90`, `+0x5c98`.., `+0x60f8`..) into the two modulation blocks and sets two words to
     `0x3fffffff`;
   * otherwise two `Lfo::render` calls - layer 1 at `+0x4ee4` with the block at `+0x5f48`, layer 0 at
     `+0x4d00` with `+0x5ac8` - with the modulation blocks as their `out` and `this + track*4 + 0x6ca4`
     (+`0x6c78`/`+0x6c4c` as the accelerometer inputs);
   * two `InstrumentManager::vibrato` calls (layer 0 from `+0x6c78`'s word, layer 1 from `+0x6c4c`'s);
   * `InstrumentManager::render(track, 0, mix, mod0, &counter)` and the same for layer 1 with `mod1`;
   * `trackFilterProcess` on `this + track*0x2c + 0x688c` and `trackFilterDcBlock` on
     `this + track*0x18 + 0x69ec`, both over the mix buffer and into the group sums;
   * the mix-down: each sample of the track mix is scaled by the track's gain (from `+0x50c8`,
     `+0x5148`, `+0x5108`, `+0x5188` and the two group gains `local_88`) with the `mul31` chains and
     saturating adds, accumulated into the group sums at `0x1227a20` (tracks 0-3) and `0x1227c20`
     (tracks 4-7), with per-track peaks at `this + track*2 + 0x6c10` and per-group peaks in the
     `local_a8` block (decayed by `* 0x7ed9 >> 15`).
3. **The master mix** (2 090-2 140): `param_1[i] = softclip(sat_add(group0[i], group1[i]))` where
   `softclip(x) = sat_add(x, sat_sub(x, mul31(mul31(x*x) * x)) >> 1)`. The C has a second, vectorised
   copy of the same arithmetic for the case where the output does not alias the sums.
4. **The FX sends/returns** (2 140-2 870): four `FxManager::render` calls with the plugs the manager
   has loaded. **v1 has none**, so each is a no-op, but the buffers around them (`0x12284a0`,
   `0x12288a0`, `this + 0xee8`..) and the `trackFilterProcess`/`trackFilterDcBlock` pairs after them
   still run.
5. **The master tail** (2 870-3 610): `param_1 += 0x12288a0`; `FxManager::render(0xb, this+0x5de0,
   param_1, ...)`; two more `trackFilterProcess`/`trackFilterDcBlock`; `bounceAudio`; the four
   `getBPM` reads and the `UNK_0017d064` table lookups that become `masterCompressor`'s four
   reference arguments; `masterCompressor(0x12288a0, ...)`; the master gain from
   `g_compressorLevel` and `this + 0x6854`/`0x6858`/`0x6264`/`0x6298`/`0x629c`; a soft limiter over
   the master buffer; the VU words; and the writes into the four caller buffers.

The two `(this + 0x6c10)`/`local_a8` peak paths and the four master words are pure bookkeeping: they
change no audio, but the fixture records them, so they must match too.

### The mixer's scratch, resolved

| object | address | offset in the port's span | role |
|---|---|---|---|
| group sums | 0x1227a20 (+0x200 per four-track group) | 0x20 | the master accumulation, summed into the output |
| send A | 0x1227e20 | 0x420 | an FX send per group |
| send B | 0x1228020 | 0x620 | the input-signal scratch (`g_renderInputSignal` only) |
| send C | 0x12284a0 | 0xAA0 | the third send |
| track mix | 0x12286a0 | 0xCA0 | what the voices render into |
| track filtered | 0x12288a0 | 0xEA0 | the DC blocker's output and the mix-down's input, later the master buffer |
| input buffer | 0x1228aa0 | 0x10A0 | the mic path, never filled in v1 |
| modulation 0/1 | 0x1228cec / 0x1228d38 | 0x12EC / 0x1338 | the two LFO blocks the voices read |

The tail, exactly: `param_1 += 0x12288a0` for the three FX-track mixes (8/9/10, each DC-blocked into
it first) and the master FX return; `trackFilterDcBlock(this + 0x6bb4, param_1, 0x12288a0)` moves the
sum into the master buffer; `bounceAudio` taps it; `masterCompressor(0x12288a0, ...)` compresses it in
place; then per sample

```text
g   = clamp(mul31_arith(this[0x6858]^2) * 0x5fffffff >>u 31) + 0x20000000     // the master gain
x   = clamp(master[i] * g * 2 >>a 0x1e & ~3)                                  // gain applied
y   = sat_add(x, sat_sub(x, mul31(mul31_arith(x^2) * x)) >> 1)                // soft clip
out = sat_add(mul31(x * (0x7fffffff - this[0x6264])), mul31(y * wet))         // dry/wet blend
peak = max(peak, out)                                                         // the VU word
out = min(0x7fffffff, mul31(this[0x6860] * out))                              // the master volume
```

`wet` is the BPM-table interpolation (`UNK_0017d064`/`+0x68`, two eight-entry `i32` tables at
0x7d064) and the compressor's third and fourth reference arguments come from `this + 0x629c` and that
table. The table is `.rodata` and belongs in a generator.

### The track loop's mix-down, decoded from the disassembly

The C for this loop reuses registers past the point of readability, so this comes from the asm at
`Synth::render+0x91c` (0xf830c..0xf84ec):

```text
per track t (the group is t >> 2, the group gain `local_88[group]`):
  ramp  = [this[t*4 + 0x50c8], this[t*4 + 0x5148]]      // lane 0: level, lane 1: pan
  target = [this[t*4 + 0x5108],
            mul31_logical(mul31_logical(mul31_logical(g1 * g2) * g3) * g4) * this[t*4 + 0x5188] >>u 31]
  step  = sqsub(target, ramp) >>a 7 per lane            // 64 frames to converge
  mix   = 0x12288a0                                     // the DC blocker's output, in place
  for i in 0..128:
      product = mix[i] * group_gain
      gain = product == 2^62 ? 0x3fffffff8 : (product >>a 28) & ~7
      gain = clamp(gain, -0x80000000, 0x7fffffff)
      a = mul31_arith(gain * ramp[0])                   // `sbfx #31` + sentinel, no clamp
      b = mul31_logical(gain * module_gain)
      sum0[i] = sat_add(sum0[i], mul31_logical(a * ramp[1]))          // 0x1227a20 + group*0x80
      sendA[i] = sat_add(sendA[i], mul31_logical(a * gain_a))         // 0x1227e20
      sendB[i] = sat_add(sendB[i], mul31_logical(a * gain_b))         // 0x1228020
      sendC[i] = sat_add(sendC[i], mul31_logical(a * gain_c))         // 0x12284a0
      out2[i]  = sat_add(out2[i], mul31_logical(b * gain_d))          // the caller's second buffer
      ramp += step                                      // after the samples are read, not before
  this[t*4 + 0x50c8] = ramp[0]; this[t*4 + 0x5148] = ramp[1]          // the ramp carries across blocks
  peaks at this[t*2 + 0x6c10] and `local_88`                          // decayed by * 0x7ed9 >> 15
```

The gain words come from the module-sends structure the sequencer holds (`getModuleSends` returns a
pointer; the mixer reads a halfword at `+0x1760` and words at `+0x1b58`/`+0x1b5c`/`+0x1b60`), from
`this + 0x6c48`, from the mute bit in `this + 0x6848` and from the two LFO blocks at `this + 0x1554`/
`+0x15a0`. The four accumulator gains (`gain_a`..`gain_d`) are four `mul31` chains over those, which
is the one part still worth reading line by line from the asm when the port lands.

`param_2` (the caller's second buffer) is written by this loop, so v1 - which has no FX tracks -
still has to produce it byte for byte for the fixture to pass.

### The mixer's state, measured while the loop was driven

* The `FxManager` has **four** slots (`FX tracks 8..11`): `0x4940 + 4 * 0xf0 = 0x4d00`, exactly the
  LFO array. Writing a fifth slot wipes the LFOs (a fixture bug that produced a very confusing diff).
* The LFO array is at `+0x4d00` with a `0x2c` stride and a **layer stride of eleven slots**, so slot 8
  is track 8 of layer 0 - the master LFO the tail renders at `+0x4e60`, `+0x4e8c` and `+0x4eb8` with
  the blocks at `+0x5d08`, `+0x5d50` and `+0x5e70`. The loop itself renders only tracks 0..7.
* The layer-1 modulation block's `out` buffer reaches `0x1228e88` (its 84th word), past the block, so
  the mixer's scratch span has to be `0x1500` bytes from `0x1227a00`.
* `Synth::resetLfo` takes the track, the layer and the caller's `params`, and uses the *Synth's*
  smoothed block for the LFO's parameters while writing the LFO's output into the caller's buffer -
  which the voices are also reading as their parameter block. A re-trigger therefore changes what the
  voices after it read. The port keeps its own copy of the modulation block per track and writes it
  back when the track's voices are done, which the mix-down sees; a voice rendering after a
  re-trigger inside the same block reads the pre-reset block. That is the one deviation, and
  `PORT_METHOD.md` records it.
* The port's `Voice` models the record from `+0x20` on; `+0x00`..`+0x1f` (the engine's area and the
  three entry points) is replaced by the trait dispatch, so a whole-mixer comparison has to zero those
  eight words on both sides.

### Where the mixer's loop stands

`render_tracks` is written and driven by `synth_render_tracks_match_the_original`, which is
`#[ignore]`d while it converges. It currently reports, per case, in this order:

| region | first diff | what it means |
|---|---|---|
| ~~a voice's `+0x174`~~ | fixed | the `centsDetune` aliasing, above |
| the level ramp `+0x50c8` | fixed | the lane-1 target chain's first factor |
| the pan ramp `+0x5148` | ~3% off | one of the four chain factors is still not the one the original multiplies |
| ~~the counters and peaks~~ | fixed | the per-track gate is a byte, and the 1000-block branch |
| the two modulation-block words | 19 and 38 | the tail's master LFOs (slots 8/9)'s shape output, ~0.03% off |
| the group sums | word 9 | one LSB, at group 0's sample 4 |

**The accumulator block is `memset` on every call** (`memset(&DAT_01327a20, 0, 0x400)` at the top of
`Synth::render`): the mix-down sums into it, so the port has to clear it too. `fe55ed7` does that, and
the group sums went from differing at word 0 to differing at word 9 by exactly one LSB. The same
commit fixed the input buffer's address (0x1228aa0, 0x200 bytes - it was pointing at 0x1228220).

Note on the group gain: it is **not** the problem. The earlier "1,024 short" was my decimal
conversion of `0x1a1dc8e`; the device's own computation is `0x842f4 + 0x199999a = 0x1a1dc8e` and the
port's formula gives exactly that.

The track filters' cutoff and level are the layer-0 modulation block's **words 8 and 9**
(`DAT_01328d0c`/`DAT_01328d10` are 0x20 and 0x24 bytes in); the port was passing 11 and 12, so every
filter ran on the wrong parameters. `a9a466c` fixes that, and **the eight track filters and the eight
DC blockers now match word for word**.

The comparison covers everything the loop owns: the setup, the LFO array and its state, the voices and
their engine dispatch, the filters, the blockers, the counters and peaks, and both ramps. Two things
are left in the loop:

1. the two modulation-block words the tail's master LFOs leave (19 and 38, ~0.03% off);
2. ~~the group sums~~ - fixed: the mix-down's first term rides the **advancing** pan lane. The
   original re-reads the ramp's lane 1 at the top of every iteration, before that iteration's step;
   the port used the fixed input value, which absorbs into the truncation for the first few samples
   and then shows as one or two LSBs. With that fixed **every word the track loop owns matches**.

So the whole track loop is verified: the setup, the LFO array and the reset seam, the voices and their
engine dispatch, the eight track filters, the eight DC blockers, the counters and peaks, both ramps,
the group gain, the mix-down and the two 128-word accumulator groups.

**What is left in the loop** is two modulation-block words - layer 0's word 38 and layer 1's word 19 -
where the port has 688567 against the device's 688384. Both blocks match everywhere else, and an LFO's
shape value depends on the destination word's *prior* content, so the cause is a write the final
content has already overwritten. Hooking the LFO renders of the writes in between is the way in.

**The group gain's formula, confirmed from the disassembly** (`0xf7d44`-`0xf7d64`):

```text
w10 = 0x199999a                       // the addend
mul x9, x9, x20                       // x20 = 0x0CCCCCD0, set at 0xf7b40/0xf7b50
lsr x9, x9, #31                       // logical
adds w9, w9, w10                      // saturating
stur w9, [x29, #-0x28]                // local_88[0], a stack slot
```

so `sat_add((input * 0x0CCCCCD0) >>u 31, 0x199999A)` is right, and the remaining 1,024 is in the
**input**: the device's value implies an input of `5,425,506` while the recorded folded `+0x684c` is
`5,414,283`, so the register feeding the multiply (`w9` at `0xf7d44`) does not hold the folded
`+0x684c`. Note that the branch two instructions earlier (`0xf7d40`) tests the *current* fold (`w10`,
the `+0x6858` one), which means the compiler kept an earlier fold in `w9` across the three later ones.
The next step is to hook `0xf7c40`-`0xf7d44` and watch `w9` - the same trace that settled the lane-1
chain.

The measurement, for the record: for `filled` track 0 the device's `local_88[0]` at the gain multiply
(`0xf83f8`) is `0x1a1dc8e = 27,385,998`, and the word it comes from - the *folded* `+0x684c`, which
the fixture records - is `5,414,283`. The formula is `sat_add(mul31(folded * 0xcccccd0), 0x199999a)`
with `0x199999a = 26,843,546`: that gives `541,428 + 26,843,546 = 27,384,974`, i.e. exactly **1,024
short** of the device's value, so the term should be `542,452` and one of the constant, the shift or a
missing addend is still off. (Both `0xccccccd` and `0xcccccd0` give the same term, so it is not the
low nibble.) Hooking the setup's own instructions (`0xf7...`, the lines that write `+0x684c` and then
`local_88`) is the direct way to read the constant and shift, the way the lane-1 chain was settled.

**Solved.** A register trace over the preamble's instructions (0xf8204-0xf82c8) gives the mapping
outright - the four factors are the four *independent* saturating complements, chained
`w28 * w23 * w22 * w27` and then `* this[0x5188]`:

| register | source |
|---|---|
| `w23` | `0x7fffffff - mul31(this[+0x6c40] * v0)` |
| `w28` | `0x7fffffff - mul31(this[+0x6c44] * v1)` |
| `w22` | `0x7fffffff - mul31(mute * this[+0x6c48])` |
| `w27` | `0x7fffffff - mul31(module * duck)` |

and `v0`/`v1` are the modulation block's words **6 and 7** (`0x1228d04`, `0x1228d08` - the block
starts at `0x1228cec`, so the second is *seven* words in, not eight). Both the level and pan ramps
then match the device exactly. The older measurements, kept for the record:

Measured with code hooks on the device, for track 0 of the `filled` case, the lane-1 chain is
`mul31(mul31(mul31(w28 * w23) * w22) * w27) * this[0x5188]` with:

| step | pc | value |
|---|---|---|
| `w28` (the chain's first factor) | — | `0x7fffffff` (1.0) |
| partial after `mul31(w28 * w23)` | `0xf8344` | `0x7bc22c39` |
| partial after `× w22` | `0xf8364` | `0x7bc22c38`, with `w22 = w27 = 0x7fffffff` |
| final `× this[0x5188]` | `0xf8378` | `this[0x5188] = 0xd2a98 = 862872` |

So `w23 = 0x7fffffff - 71,103,942`, and the *earlier* product at `0xf8254` is
`x10 = 0xfdf114b2841dd69b` from `x13 = 0x7fffffff` and `x17 = -69,064,347` (the raw `d04`), with
`x25 = 0x43dd3c6 = 71,103,942` at that point. The narrowing of `x10` cannot produce `x25` (a logical
`>> 31` gives `0xfbe22965`, an arithmetic one `0xffbe2296`), so one of the two chains feeding `w23`
is not the multiply I mapped it to - `x25` is set by `sxtw x25, w9` two instructions earlier, so the
next thing to hook is `0xf8250` to see where that value comes from. For track 1 the same dump is
`x17 = 663,280` and `x25 = 0xfffffffffba7c872`, which rules out a fixed relationship between them.

The older numbers, for track 0:

Measured for track 0 of the `filled` case, the preamble's four complements are
`[0x7fffffff, 2145157886, 0x7fffffff, 0x7fffffff]` where the device's chain product implies
`0.9667` instead of my `0.9989` - so one factor is roughly 0.967 against my 1.0. The inputs are
`d04 = -69064347`, `d08 = -72317119` (raw, because the plug flags leave the raw word in place), the
mute mask `0x6848 >> track & 1 = 0`, `module = 0`, `this[0x6c40] = this[0x6c44] = 0x7fffffff`,
`this[0x6c48] = -6517706`, and the duck word `0x7fffffff - this[0x5ea0] = 2141718728`. The four
factors the original multiplies, in the order the disassembly shows them (0x831c on), are the
module's complement, the `+0x6c40` word's, one that crosses the first modulation word *again* with
the `+0x6c44` chain, and the mute's - the interleaving around `0x829c` is where the last ambiguity
is.

The words *before* those match, so the LFO phase (both layers, including the reset seam) and the
setup are right.

**The modulation blocks are the next blocker, and they are the tail's doing.** Layer 1 matches words
0..18 and differs at word 19; layer 0 differs from word 0 on. That is not the loop's LFOs - the
device's own parameter region (0x51c8..0x6860, which includes every smoothed block the LFOs are given
as parameters) matches word for word. It is the FX/master section, which renders three more LFOs -
slots 8, 9 and 10 at `+0x4e60`, `+0x4e8c` and `+0x4eb8`, with the parameter blocks at `+0x5d08`,
`+0x5d50` and `+0x5e70`, and hands them `&DAT_01328cec` (layer 0) as their output. They run at C lines
2755, 2812 and 2283, so *after* the track loop, and nothing downstream can match until that section is
ported.

That section (C lines 2690-2870) is: `trackFilterDcBlock(this + 0x6b70, mix, 0x12288a0)` for the
master track, the three LFO renders, four `FxManager::render` calls (no-ops in v1), the three
FX-track mixes each through its own `trackFilterProcess` and `trackFilterDcBlock` into 0x12288a0 and
then added into `param_1`, and the master DC blocker that moves `param_1` into 0x12288a0 for
`bounceAudio` and the compressor.

**`+0x174` is solved, and it is a layout fact, not an arithmetic one.** A write watchpoint on voice
0's `+0x174` shows exactly one write in the whole call - `Voice::renderVoice`'s store at `0x13dbcc` -
and the value it writes is `0xff3bb6c2`, which the *device's own* `centsDetune` table reproduces
exactly: `table[225] * centsDetune[0] >> 30 & ~1` with the table's element 0 equal to **6449518**,
not the `0x20000000` the port computes. The reason is that on the device the two modulation blocks
*overlap the head of `Tuning::centsDetune`*:

```text
layer-0 block   0x1228cec   (0x54 words = 0x150 bytes → 0x1228e3c)
layer-1 block   0x1228d38   (0x54 words = 0x150 bytes → 0x1228e88)
Tuning::centsDetune  0x1228d88   (2401 words → 0x122b30c)
```

`centsDetune` starts 0x50 bytes into the layer-1 block's 0x150, so an LFO writing `out[dest]` with a
high destination - or even the marker at `out[18]` - *is* writing the detune table. That is real
device behaviour on the voice path, and it is reachable in v1 whenever a modulation parameter selects
a high destination, so the port has to reproduce it rather than compute `centsDetune` into a private
static.

The fix, and it is small: the voice path should take the detune *value* (`cents_detune_at(index)` is
still the right helper for callers whose table is not aliased), and the mixer must take it from its own
scratch - which therefore has to span `0x1227a00` through `0x122b30c` (3651 words), with the table at
word 1250. `VoiceHost.detune_index: u16` becomes `detune: i32`; the voice and manager fixtures pass
`cents_detune_at(case.detune_index)` as they do today.

The older, still-valid part of the analysis:

The `+0x174` diff is precise and surprising: for a voice whose every other field matches (note,
variant, the ADSR words, the step at `+0x17c`, the bend and vibrato, the legato byte, and both the
current frequency at `+0x170` and the previous one at `+0x178`), the port's target is
`note_frequency(note, variant < 4, centsDetune[0])` while the device's is a value that is **not**
`table[note] * detune >> 30` for any table entry or any `centsDetune` entry (implied detunes come out
at 0.003 of full scale, and the table's whole range is 0.5 to 1.0). `Voice::renderVoice` does store
exactly `(table[note] * detune) >> 30 & ~1` at `+0x174` (0x13dbcc), so something writes it
afterwards - the fresh path of `Voice::noteOn` stores the *same* value at both `+0x174` and
`+0x178`, and the legato path does not touch it. The next thing to check is which of `renderVoice`'s
callers can overwrite it, and whether the fixture's voice went through `noteOn` at all. The three send buffers are not compared: their gains are the one part of the
preamble's `mul31` chains that is not decoded yet.

The test's own machinery, worth keeping: it rebuilds the `Synth`'s structured parts (23 LFOs, 13
filters, 12 blockers, 44 voices) from the fixture's word buffer, runs the loop, writes the objects
back into the words, and compares only the regions the loop owns - with the port's deliberate gaps
masked on *both* sides (the engine area, the three entry points, the engine's state block, the bytes
the original's constructor leaves untouched).

## The seam decisions a resuming session must not undo

* **`EngineVoice` (in `voice.rs`)** replaces the original's three per-voice function pointers
  (`+0x08` render, `+0x10` noteOn, `+0x18` noteOff). `InstrumentManager::render` should call
  `Voice::render_voice`, and the engine's state block at `+0x58`..`+0x16f` belongs to the engine.
  `SynthHost::reset_lfo` is the same kind of seam for the `g_synth` global that `Voice::noteOn`
  reaches.
* **Host values are arguments, never globals**: `VoiceHost { detune_index, auto_legato_glide,
  last_note }` (the sequencer's `centsDetune` index, `g_autoLegatoGlide`, `Voice::s_lastNote`).
  `masterCompressor` takes its whole state in `MasterCompressor`. `Lfo::render` takes `bpm`, `pitch`
  and `pitch_dz` in place of `Sequencer::getBPM` and the two accelerometer globals. Keep going that
  way: the chain owns one of each.
* **Embedded tables are generated**: `tools/gen-lfo-tables.py` and `tools/gen-voice-tables.py` read
  the `.so`; both have a `--check` mode. `Tuning::centsDetune` is the exception - it is `.bss` that
  `initTuning` computes, so `tuning.rs` computes it and the fixture checks all 2 401 words against the
  original's own output (the harness stubs `exp2`).
* **The ADSR types are still split**: `adsr::Adsr` (six words, the device's layout),
  `digital::DigitalAdsr` (four fields) and `sample_player_gain::Adsr`. The wired chain will need one
  of them as canonical, with adapters at the `EngineVoice::render` boundary - the engines update the
  level per frame, so the adapter must copy the four shared fields back.

## Fixture technique worth reusing

`make_host_fixtures.py`'s `voice_fixtures` writes Python stubs over the original's function pointers
(found with `opzso.stub_address`) and records the registers each stub was called with. That pins a
function whose callees are engines without pulling the engines in. Two traps already paid for:

* The three pointers are 8 bytes wide - write them with `write_u64`, and zero *both* halves of each
  slot in the recorded words or the stub address leaks into the comparison.
* Register arguments are easy to get backwards. `Voice::renderVoice` is `(this, out, params)`, and a
  fixture with `out` and `params` swapped silently pins the wrong thing - it cost two debugging
  rounds before the glide cases made sense. Check a call's argument order against the C *and* the
  disassembly before trusting a fixture that "fails oddly".

## Measured facts about the remaining pieces

* `Synth::render` is the global mixer. Its per-track work is: `Lfo::render` twice (or once) per layer,
  `InstrumentManager::render` twice (layers 0/1), `trackFilterProcess`, `trackFilterDcBlock`; then
  `masterCompressor` and `bounceAudio` over the master block.
* The mix buffers are library `.bss` scratch, 0x200 bytes apart: `0x12284a0`, `0x12286a0`,
  `0x12288a0`, plus `0x1228cec`/`0x1228d38` (small, and near the shared parameter block at
  `0x1228ca0`). The port must own them rather than reach for statics.
* `trackFilterProcess`'s tables are indexed `bank * 0x104 + row * 4` bytes - **0x104, not the 0x924
  between one table and the next**. Both indices read below the table (mode to -16, row to -64), so
  `filter_tables.rs` carries that padding.
* The filter's ramp flag does not only enable a pass: it *replaces* the value the state's cutoff word
  ramps toward with `(0x1fffffff - cutoff)` (zeroed when negative) `<< 2`, before anything else reads
  the parameter. The row weight still uses the original `(cutoff & 0x1ffffff) << 6`.
* `Synth::resetLfo(this, track, layer, params)` resets the LFO at
  `this + track*0x2c + layer*0x1e4 + 0x4d00` with the parameter block at
  `this + track*0x48 + layer*0x480 + 0x5ac8`, and repeats the first one when `layer == 1` and
  `[g_sequencer + 0x1c] == 0`. The LFO array's layer stride is *eleven* slots, so slot 11 is both
  track 11 of layer 0 and track 0 of layer 1.
* One `Lfo` is 0x28 bytes of state inside a 0x2c-byte slot: `+0x07` and `+0x1e`..`+0x1f` are bytes no
  LFO path touches, and a byte-exact port carries them anyway.
* The random value comes from one library-wide LCG (`randSeed`, shared with `AnalogA`'s noise), so
  `Lfo` takes `&mut seed` rather than owning one. The chain must own exactly one and hand it to both.
* `Synth` is at least 0x6d2f bytes (the mute byte at `+0x6d2e`); the harness allocates 0x7000.
* `InstrumentManager` owns 44 voices at a 0x190 stride; `Voice::s_lastNote` (16 bytes) is at
  `0x16e8b48`, `g_autoLegatoGlide` at `0x1de770`, `g_synth` at `0x1227798`,
  `Tuning::centsDetune` at `0x1228d88` (2 401 words), `g_bouncingAudio` at `0x12322a0`,
  `bounceWritePos` at `0x1232298` and `bounceBuffer` at `0x122de98`.
* `tools/resolve-got.py <slot>...` resolves a GOT slot to its symbol and address from
  `.rela.dyn`/`.rela.plt` - that is how the globals above were found (`python3 tools/resolve-got.py
  0x1d58f0`).
